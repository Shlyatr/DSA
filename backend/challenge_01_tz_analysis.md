# Анализ технического задания: Challenge 01 / Jana Address

Данный документ представляет собой подробный разбор технического задания по первому кейсу хакатона **Jana Post Terricon Valley Hackathon 2026** — **Challenge 01 / Jana Address** («Автоматический разбор и нормализация адресов»).

---

## 1. Общие сведения и бизнес-контекст

### 1.1. Проблема
В текущей базе данных компании Jana Post адреса клиентов хранятся одной произвольной строкой в том виде, в котором их вводит пользователь.

Примеры входных строк:
* `"66квартал 12дом 69квартира"`
* `"Ул. Курильская 9 кв 1"`
* `"Туран 55/6 магазин береке 4подьезд 9этаж"`
* `"город Алматы/Алматы қаласы, Мкр Аксай За, 59, кв 70"`

**Из-за нестандартизированных данных возникает ряд проблем:**
* Не работает аналитика по городам и регионам.
* Невозможно автоматически рассчитать зону доставки.
* Курьеры вынуждены уточнять по телефону детали адреса (номер квартиры, подъезд, этаж).

### 1.2. Цель
Разработать решение, которое раскладывает произвольную текстовую строку адреса на точные структурированные поля, выполняет нормализацию и восстанавливает недостающие справочные данные (район города, жилой массив/микрорайон) по собственному справочнику.

---

## 2. Формат данных и правила заполнения полей

### 2.1. Входные данные
* **`train.json`** — файл с несколькими тысячами реальных адресных строк из базы Jana Post.
* **`sample_input.json`** — пример структуры входного файла, подаваемого на проверку:
  ```json
  {
    "id": "rec_00417",
    "raw_address": "город Алматы/Алматы қаласы, Мкр Аксай За, 59, кв 70"
  }
  ```

### 2.2. Выходные данные (`sample_output.json`)
Каждая входная запись должна иметь соответствующий ответ. Пропускать записи запрещено.

```json
{
  "id": "rec_00417",
  "raw_address": "город Алматы/Алматы қаласы, Мкр Аксай За, 59, кв 70",
  "province": "Алматы",
  "city": "Алматы",
  "district": "Ауэзовский",
  "living_area": null,
  "street_type": "микрорайон",
  "street_name": "Аксай За",
  "house": "59",
  "apartment": "70",
  "entrance": null,
  "floor": null,
  "landmark": null,
  "confidence": 0.91
}
```

### 2.3. Спецификация полей и правила обработки

| Поле | Описание и правила заполнения |
| :--- | :--- |
| **`id`** | Идентификатор записи из исходного файла (без изменений). |
| **`raw_address`** | Исходная строка адреса без изменений (нужна для удобства сверки). |
| **`province`** | Область или город республиканского значения в прямом порядке (например: `"Актюбинская область"`, `"Алматы"`). |
| **`city`** | Название города без слов «город», «пос.», без казахской половины при склейке (например: `"Актобе"`, `"Боралдай"`). |
| **`district`** | Название района города/области без слова «район» (например: `"Илийский"`, `"Ауэзовский"`). |
| **`living_area`** | Микрорайон или ЖК, когда улица указана отдельно (например: `"Пришахтинск"`, `"Томирис"`). |
| **`street_type`** | Тип улицы отдельным словом (`улица`, `проспект`, `микрорайон`, `переулок`, `квартал`). Если в строке не указан и определить нельзя — `null`. |
| **`street_name`** | Название улицы без типа, ровно в том виде и падеже, как в строке. Опечатки не исправляются (например: `"казибек би"` так и остается). |
| **`house`** | Номер дома с дробью и литерой (например: `"1/2"`, `"12а"`). Значения `"1/2"` и `"1"` считаются разными. |
| **`apartment`** | Только номер квартиры, без слов «кв» (например: `"70"`). |
| **`entrance`** | Только номер подъезда, без слова «подъезд». |
| **`floor`** | Только номер этажа, без слова «этаж». |
| **`landmark`** | Ориентир, если присутствовал в строке (например: `"магазин береке"`). |
| **`confidence`** | Оценка уверенности модели/пайплайна от `0` до `1`. В автоматическую метрику не входит, проверяется жюри. |

> **Важно:** Поле, которое не удалось определить или которого нет в строке, заполняется как `null`.

## 3. Границы задачи и краевые случаи (Edge Cases)

В данных присутствуют следующие инженерные сложности, которые необходимо учесть:
1. **Слитное написание:** `"66квартал"`, `"Назарбаева8"`, `"11дом"`, `"4подьезд"`.
2. **Дробные и литерные номера:** `1/2`, `33/1`, `55/6`, `12а` — дробные части терять нельзя.
3. **Двуязычие и склейки:** Двуязычные наименования через слэш (`"город Актобе/Ақтөбе қаласы"`).
4. **Смешение языков/алфавитов:** Использование латиницы (`"flat 191"`, `"kv 12"`).
5. **Путаница сущностей:** Номер микрорайона легко спутать с номером дома (`"Нурсити 2 микрорайон 11дом 5 подьезд 239 кв"`).
6. **Дублирование и некорректная иерархия:** Повтор города в строке, указание района вместо города.
7. **Опечатки и синтаксис:** Ошибки в словах (`"подьезд"` вместо `"подъезд"`), лишние пробелы, невидимые служебные символы.
8. **Ориентиры прямо в тексте:** `"магазин береке"`, `"Qazpost Солнечный"`.

## 4. Требования к справочнику

Организаторы **не предоставляют** готовый справочник адресов. Сбор и подготовка геоданных — часть задачи команды.

* **Возможные источники:**
  * OpenStreetMap (дамп по Казахстану).
  * Реестры `data.egov.kz`.
  * Справочник КАТО (Классификатор административно-территориальных объектов).
  * Открытые геокодеры (используются на этапе подготовки базы).
* **Применение справочника:**
  * Если района или жилого массива нет в строке, решение должно поднять их из сформированного справочника.

## 5. Требования к сдаче и технические ограничения

1. **REST API:**
   * Наличие метода для пакетной обработки адресов (жюри прогонит скрытый набор через API).
2. **Веб-интерфейс (UI):**
   * Экран для загрузки файла, просмотра результатов разбора и возможности ручной правки неуверенных записей (`confidence`).
3. **Автономность и контейнеризация:**
   * Запуск одной командой: `docker compose up`.
   * **Ограничение сети:** Во время финального прогона сеть отключена. Все справочники, словари, NLP-модели и зависимости должны находиться внутри Docker-образа.
4. **Производительность:**
   * Время разбора: не более **5 минут на 1000 записей**.
   * Время запуска контейнера: не более **3 минут** (загрузка справочников в память при старте в лимит 5 минут не входит).
5. **Файл README:** Пошаговая инструкция по запуску и описанием архитектуры.

## 6. Критерии оценивания

Итоговая оценка команды формируется из 4 компонентов:

```
Итоговый балл = (Метрики * 0.45) + (Инженерия * 0.30) + (Интерфейс * 0.15) + (Презентация * 0.10)
```

### 6.1. Детализация оценки

| Критерий | Вес | Детали |
| :--- | :---: | :--- |
| **Метрики на скрытом наборе** | **45%** | Автоматическая проверка точности разбора строк на скрытом наборе данных. |
| **Инженерная часть** | **30%** | Качество сбора и работы со справочником (восстановление районов/ЖК), архитектура, автономность, качество кода. |
| **Удобство интерфейса** | **15%** | Удобство экрана ручной правки, отображение `confidence`, загрузка/скачивание файлов. |
| **Презентация** | **10%** | Доклад, защита архитектуры и обоснование принятых решений. |

### 6.2. Формула автоматической метрики (45% от итогового балла)

Автоматическая метрика считается строго по посимвольному совпадению текста (приведенного к нижнему регистру и очищенного от пунктуации и лишних пробелов):

* **Точность адреса (60% от метрики):** Верно определены `province`, `city`, `street_name`, `house`.
* **Точность деталей (25% от метрики):** Верно извлечены `apartment`, `entrance`, `floor`.
* **Точность справочных полей (15% от метрики):** Верно извлечены `district` и `living_area` **только по тем записям, где они физически есть в исходной строке**.

> **Обратите внимание:**
> 1. Поле `street_type` не входит в автоматическую метрику, так как в части строк тип отсутствует (оценивается жюри на защите).
> 2. Восстановление недостающих `district` и `living_area` из справочника (когда их нет в исходном тексте) **не входит в автоматическую метрику**, а оценивается жюри в рамка **Инженерного критерия (30%)** на защите.
